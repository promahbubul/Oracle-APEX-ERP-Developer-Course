**তারিখ:** ৩০ নভেম্বর ২০২৬, সোমবার
**সময়:** সন্ধ্যা ৭:০০ থেকে রাত ১০:০০
**সপ্তাহ:** ৪ | **ধাপ:** ১ (কম্পিউটার ও ডাটাবেসের বেসিক)

- 2NF-এর নিয়ম

## ১. 2NF-এর নিয়ম (৩০ মিনিট)

একটা টেবিল **2NF**-এ থাকবে, যদি:

1. টেবিলটা **1NF**-এ থাকে
2. Key-র বাইরের প্রতিটা কলাম **পুরো Primary Key**-র উপর নির্ভর করে, Key-র **একটা অংশের** উপর নয়

Key-র একটা অংশের উপর নির্ভর করাকে বলে **Partial Dependency**।

> **জরুরি:** Partial Dependency হতে হলে Key-র একাধিক অংশ থাকতে হয়। তাই **PK একটা কলামের হলে টেবিল 1NF থাকলেই 2NF-এ থাকে।** 2NF মূলত **Composite Key**-র টেবিলের জন্য।

### উদাহরণ

একটা অর্ডারে কয়েকটা আইটেম থাকে।

**ORDER_ITEM_FLAT**। PK: `(order_no, item_id)`

| ORDER_NO | ORDER_DATE | BUYER_NAME | BUYER_COUNTRY | ITEM_ID | ITEM_NAME | UNIT | QTY | UNIT_PRICE |
|---|---|---|---|---|---|---|---|---|
| ORD-101 | 2026-11-01 | H&M | Sweden | 1 | Single Jersey | Kg | 1200 | 4.20 |
| ORD-101 | 2026-11-01 | H&M | Sweden | 5 | Button 18L | Pcs | 20000 | 0.02 |
| ORD-102 | 2026-11-03 | Zara | Spain | 1 | Single Jersey | Kg | 800 | 4.25 |
| ORD-102 | 2026-11-03 | Zara | Spain | 6 | Zipper 7 inch | Pcs | 5000 | 0.15 |

এটা 1NF-এ আছে: এক ঘরে এক মান, পুনরাবৃত্ত কলাম নেই, PK আছে। তবু `ORD-101`-এর তারিখ দুইবার, `Single Jersey` দুইবার।

## ২. Partial Dependency খোঁজা (৪০ মিনিট)

প্রতিটা কলামের জন্য প্রশ্ন করো: **"এটা জানতে কি পুরো Key লাগে, নাকি একটা অংশই যথেষ্ট?"**

| কলাম | কী লাগে | Dependency | ধরন |
|---|---|---|---|
| ORDER_DATE | শুধু order_no | `order_no → order_date` | **Partial** ❌ |
| BUYER_NAME | শুধু order_no | `order_no → buyer_name` | **Partial** ❌ |
| BUYER_COUNTRY | শুধু order_no | `order_no → buyer_country` | **Partial** ❌ |
| ITEM_NAME | শুধু item_id | `item_id → item_name` | **Partial** ❌ |
| UNIT | শুধু item_id | `item_id → unit` | **Partial** ❌ |
| QTY | দুইটাই | `(order_no, item_id) → qty` | **পুরো** ✅ |
| UNIT_PRICE | দুইটাই | `(order_no, item_id) → unit_price` | **পুরো** ✅ |

`UNIT_PRICE` খেয়াল করো: `Single Jersey`-এর দাম `ORD-101`-এ 4.20, `ORD-102`-এ 4.25। দাম নির্ভর করে **কোন অর্ডারের কোন আইটেম** তার উপর, তাই পুরো Key লাগে।

> **`UNIT_PRICE` কি আইটেমের তথ্য, নাকি অর্ডারের লাইনের?** ব্যবসার নিয়মের উপর নির্ভর করে। আইটেমের দাম সব জায়গায় একই হলে এটা `item`-এ যেত। এখানে অর্ডারভেদে দাম আলাদা, তাই লাইনে। ডিজাইনের আগে এটা জেনে নিতে হয়।

### কী সমস্যা হচ্ছে

| Anomaly | উদাহরণ |
|---|---|
| **Insert** | নতুন আইটেম, কিন্তু এখনো কোনো অর্ডারে নেই, রাখা যায় না |
| **Update** | `ORD-101`-এর তারিখ বদলালে দুই রো বদলাতে হবে |
| **Delete** | `ORD-102` মুছলে `Zipper 7 inch` আইটেমটাই হারিয়ে যাবে |

## ৩. ভেঙে 2NF-এ আনা (৪০ মিনিট)

**নিয়ম:** যে কলাম Key-র যে অংশের উপর নির্ভর করে, তাকে সেই অংশসহ আলাদা টেবিলে নাও।

```
order_no-র উপর নির্ভর    → অর্ডারের টেবিল
item_id-র উপর নির্ভর     → আইটেমের টেবিল
দুইটার উপর নির্ভর        → মূল টেবিলে থাকবে
```

**N2_ORDER** (PK: order_no)

| ORDER_NO | ORDER_DATE | BUYER_NAME | BUYER_COUNTRY |
|---|---|---|---|
| ORD-101 | 2026-11-01 | H&M | Sweden |
| ORD-102 | 2026-11-03 | Zara | Spain |

**N2_ITEM** (PK: item_id)

| ITEM_ID | ITEM_NAME | UNIT |
|---|---|---|
| 1 | Single Jersey | Kg |
| 5 | Button 18L | Pcs |
| 6 | Zipper 7 inch | Pcs |

**N2_ORDER_ITEM** (PK: order_no, item_id)

| ORDER_NO | ITEM_ID | QTY | UNIT_PRICE |
|---|---|---|---|
| ORD-101 | 1 | 1200 | 4.20 |
| ORD-101 | 5 | 20000 | 0.02 |
| ORD-102 | 1 | 800 | 4.25 |
| ORD-102 | 6 | 5000 | 0.15 |

চেনা লাগছে? `N2_ORDER_ITEM` হলো **Junction Table**। একটা অর্ডারে অনেক আইটেম, একটা আইটেম অনেক অর্ডারে। ক্লাস ১৪-এ শিখেছিলে, "জোড়ার তথ্য জোড়ার টেবিলে": 2NF-এর নিয়মটাই সেই কথা।

### SQL-এ বানাও

সপ্তাহ ৩-এর টেবিলের সাথে নাম যাতে না মেলে, তাই নামের আগে `n2_` দিয়েছি।

```sql
SET DEFINE OFF

CREATE TABLE n2_order (
    order_no       VARCHAR2(20),
    order_date     DATE NOT NULL,
    buyer_name     VARCHAR2(100) NOT NULL,
    buyer_country  VARCHAR2(50),
    CONSTRAINT n2_order_pk PRIMARY KEY (order_no)
);

CREATE TABLE n2_item (
    item_id    NUMBER(10),
    item_name  VARCHAR2(100) NOT NULL,
    unit       VARCHAR2(20)  NOT NULL,
    CONSTRAINT n2_item_pk PRIMARY KEY (item_id),
    CONSTRAINT n2_item_name_uk UNIQUE (item_name)
);

CREATE TABLE n2_order_item (
    order_no    VARCHAR2(20),
    item_id     NUMBER(10),
    qty         NUMBER(12,3) NOT NULL,
    unit_price  NUMBER(10,2) NOT NULL,
    CONSTRAINT n2_order_item_pk PRIMARY KEY (order_no, item_id),
    CONSTRAINT n2_order_item_order_fk FOREIGN KEY (order_no) REFERENCES n2_order (order_no),
    CONSTRAINT n2_order_item_item_fk FOREIGN KEY (item_id) REFERENCES n2_item (item_id)
);

INSERT INTO n2_order VALUES ('ORD-101', DATE '2026-11-01', 'H&M', 'Sweden');
INSERT INTO n2_order VALUES ('ORD-102', DATE '2026-11-03', 'Zara', 'Spain');

INSERT INTO n2_item VALUES (1, 'Single Jersey', 'Kg');
INSERT INTO n2_item VALUES (5, 'Button 18L', 'Pcs');
INSERT INTO n2_item VALUES (6, 'Zipper 7 inch', 'Pcs');

INSERT INTO n2_order_item VALUES ('ORD-101', 1, 1200, 4.20);
INSERT INTO n2_order_item VALUES ('ORD-101', 5, 20000, 0.02);
INSERT INTO n2_order_item VALUES ('ORD-102', 1, 800, 4.25);
INSERT INTO n2_order_item VALUES ('ORD-102', 6, 5000, 0.15);
COMMIT;
```

### Anomaly গেল কি না মিলিয়ে দেখো

```sql
-- Insert: অর্ডার ছাড়াই নতুন আইটেম
INSERT INTO n2_item VALUES (7, 'Main Label', 'Pcs');

-- Update: ORD-101-এর তারিখ একটা রো-তেই বদলাবে
UPDATE n2_order SET order_date = DATE '2026-11-02' WHERE order_no = 'ORD-101';

-- Delete: ORD-102-র লাইন মুছলেও Zipper থাকে
DELETE FROM n2_order_item WHERE order_no = 'ORD-102';
SELECT * FROM n2_item;

ROLLBACK;
```

### কিন্তু এখনো একটা সমস্যা বাকি

`N2_ORDER`-এ দেখো: একই Buyer-এর অনেক অর্ডার হলে `buyer_name` আর `buyer_country` আবার বারবার আসবে। এটা 2NF ভাঙে না, কারণ PK একটা কলামের। কিন্তু সমস্যা আছে। এটা ঠিক করবে **3NF**, কাল।

## ৪. আলাদা ID দিলে কি সমস্যা চলে যায়? (১০ মিনিট)

ক্লাস ১৪-এ শিখেছিলে, লেনদেনের টেবিলে আলাদা ID দেওয়া ভালো। ধরো:

| ORDER_ITEM_ID (PK) | ORDER_NO | ORDER_DATE | ITEM_ID | ITEM_NAME | QTY |
|---|---|---|---|---|---|
| 1 | ORD-101 | 2026-11-01 | 1 | Single Jersey | 1200 |
| 2 | ORD-101 | 2026-11-01 | 5 | Button 18L | 20000 |

PK এখন এক কলামের, তাই নিয়ম অনুযায়ী এটা 2NF-এ। **কিন্তু সমস্যাগুলো ঠিকই আছে:** `ORDER_DATE` আর `ITEM_NAME` এখনো বারবার।

**তাই আলাদা ID দিলেই ডিজাইন ভালো হয় না।** প্রশ্নটা সবসময় আসল Key ধরে করো: "এই রো আসলে কীসের? কোন জিনিস দিয়ে এই রো চেনা যায়?"

## ৬. হোমওয়ার্ক

1. নিজের ভাষায় লেখো: Partial Dependency কী? একটা গার্মেন্টসের উদাহরণ দাও।
2. এই টেবিল 2NF-এ ভাঙো (খাতায়)। PK: `(student_id, course_id)`। কলাম: student_name, course_name, teacher_name, enroll_date, grade।
3. ক্লাস ১৭-এর `style_color` টেবিলে `style_name` কলাম যোগ করলে 2NF থাকবে কি? কেন?

<summary>হোমওয়ার্ক ২ ও ৩-এর সমাধান</summary>

**২:**
- **STUDENT:** student_id (PK), student_name
- **COURSE:** course_id (PK), course_name, teacher_name
- **ENROLLMENT:** student_id (FK), course_id (FK), enroll_date, grade। PK: `(student_id, course_id)`

**৩:** থাকবে না। PK হলো `(style_no, color_name)`, কিন্তু `style_name` শুধু `style_no`-এর উপর নির্ভর করে। এটা Partial Dependency।

</details>

## ৭. কুইজ

1. 2NF-এর দুইটা শর্ত কী?
2. Partial Dependency কী?
3. PK এক কলামের হলে আর 1NF-এ থাকলে টেবিলটা 2NF-এ থাকে কি?
4. `(order_no, item_id)` PK-র টেবিলে `item_name` কলাম থাকলে কী সমস্যা?
5. আলাদা ID দিলে কি Redundancy-র সমস্যা চলে যায়?

<details>
<summary>উত্তর দেখো</summary>

1. টেবিল 1NF-এ থাকবে, আর Key-র বাইরের প্রতিটা কলাম পুরো Key-র উপর নির্ভর করবে
2. Key-র বাইরের কোনো কলাম Composite Key-র শুধু একটা অংশের উপর নির্ভর করা
3. হ্যাঁ, কারণ Partial Dependency হওয়ার সুযোগই নেই
4. এটা শুধু `item_id`-এর উপর নির্ভর করে। Partial Dependency, তাই আলাদা `item` টেবিলে যাবে
5. না। নিয়মে 2NF দেখালেও একই তথ্য বারবার থাকতে পারে

</details>

## সারাংশ

- 2NF = 1NF + Key-র বাইরের কলাম পুরো Key-র উপর নির্ভর
- Partial Dependency মানে Key-র একটা অংশের উপর নির্ভর, শুধু Composite Key-তে হয়
- ঠিক করার উপায়: কলামটাকে Key-র সেই অংশসহ আলাদা টেবিলে নেওয়া
- পুরো Key-র উপর নির্ভর তথ্য জোড়ার টেবিলে থাকে
- আলাদা ID দিলেই ডিজাইন ঠিক হয় না

**পরের ক্লাস:** 3NF (Third Normal Form), Denormalization কখন করা হয়।
