## ২. Data Redundancy (২০ মিনিট)

**Data Redundancy** মানে একই তথ্য একাধিক জায়গায় জমা থাকা।

উপরের টেবিলে:

| তথ্য | কতবার লেখা হয়েছে |
|---|---|
| `H&M` আর `Sweden` | ৩ বার |
| `HM-TS-001` আর `Basic T-Shirt` | ২ বার |

মাত্র ৫টা রো-তেই এই অবস্থা। ১ লাখ অর্ডারে H&M-এর নাম হয়তো ২০ হাজার বার লেখা থাকবে।

**এতে ক্ষতি কী:**
- জায়গা নষ্ট হয়
- প্রতিবার টাইপ করতে হয়, তাই ভুল হয়: `H&M`, `HM`, `H & M`
- রিপোর্টে একই Buyer তিন জন হয়ে দেখায়
- একটা তথ্য বদলাতে অনেক রো বদলাতে হয়

তবে সব পুনরাবৃত্তি Redundancy না। `orders` টেবিলে `buyer_id = 1` অনেকবার থাকাটা স্বাভাবিক, কারণ সেটা সম্পর্ক বোঝায়। সমস্যা হলো **নাম আর দেশের মতো তথ্য** বারবার রাখা।

## ৩. Anomaly (৫০ মিনিট)

**Anomaly** মানে ডাটা ঢোকানো, বদলানো বা মোছার সময় তৈরি হওয়া অস্বাভাবিক সমস্যা। Redundancy থেকেই এগুলো আসে।

### Insert Anomaly: যা ঢোকাতে চাই, ঢোকানো যায় না

নতুন Buyer `Walmart` এলো, কিন্তু এখনো অর্ডার দেয়নি। তার তথ্য রাখব কীভাবে?

```sql
INSERT INTO order_flat (buyer_name, buyer_country)
VALUES ('Walmart', 'USA');
```

```
ORA-01400: cannot insert NULL into ("LEARN"."ORDER_FLAT"."ORDER_NO")
```

অর্ডার ছাড়া Buyer রাখাই যাচ্ছে না। একটা ভুয়া অর্ডার বানিয়ে রাখলে আবার রিপোর্ট ভুল হবে।

### Update Anomaly: এক জায়গায় বদলালে বাকিগুলো পুরনো থাকে

`Ctrl + Enter` দিয়ে একটা একটা করে চালাও:

```sql
-- Buyer-এর দেশের লেখা বদলাতে গিয়ে শুধু একটা রো বদলালাম
UPDATE order_flat
SET    buyer_country = 'SE'
WHERE  order_no = 'ORD-101';

SELECT order_no, buyer_name, buyer_country
FROM   order_flat
WHERE  buyer_name = 'H&M';
```

ফলাফল:

```
ORDER_NO  BUYER_NAME  BUYER_COUNTRY
--------  ----------  -------------
ORD-101   H&M         SE
ORD-102   H&M         Sweden
ORD-103   H&M         Sweden
```

এখন H&M কোন দেশের? ডাটাবেস নিজেই নিজের সাথে মিলছে না। একে বলে **Data Inconsistency**।

```sql
ROLLBACK;     -- বদলানোটা বাতিল
```

### Delete Anomaly: এক তথ্য মুছলে আরেক তথ্যও হারায়

Primark-এর একটাই অর্ডার। সেটা বাতিল করে মুছলে কী হয়?

```sql
DELETE FROM order_flat WHERE order_no = 'ORD-105';

SELECT * FROM order_flat WHERE buyer_name = 'Primark';
```

কোনো রো নেই। অর্ডারের সাথে **Primark যে আমাদের Buyer, সেই তথ্যও গেল**, আর `PM-JN-001` স্টাইলের তথ্যও গেল।

```sql
ROLLBACK;     -- মোছাটা বাতিল
```

### তিনটা একসাথে

| Anomaly | সমস্যা | গার্মেন্টসের উদাহরণ |
|---|---|---|
| **Insert** | একটা তথ্য রাখতে অন্য তথ্য লাগে | অর্ডার ছাড়া Buyer রাখা যায় না |
| **Update** | একই তথ্য অনেক জায়গায় বদলাতে হয় | Buyer-এর ঠিকানা ২০ হাজার রো-তে |
| **Delete** | মুছলে দরকারি তথ্য হারায় | শেষ অর্ডার মুছলে Buyer হারায় |

## ৪. Functional Dependency ও Normalization (৩০ মিনিট)

### Functional Dependency

**Functional Dependency** মানে: একটা কলামের মান জানলে আরেকটা কলামের মান নিশ্চিতভাবে জানা যায়। লেখা হয় `A → B`, পড়া হয় "A দিয়ে B ঠিক হয়"।

`order_flat` টেবিলে:

| Dependency | মানে |
|---|---|
| `order_no → order_date, order_qty, unit_price` | অর্ডার নম্বর জানলে তারিখ, পরিমাণ, দাম জানা যায় |
| `order_no → style_no` | প্রতিটা অর্ডারের একটাই স্টাইল |
| `style_no → style_name, buyer_name` | স্টাইল নম্বর জানলে নাম আর Buyer জানা যায় |
| `buyer_name → buyer_country` | Buyer জানলে দেশ জানা যায় |

উল্টোটা সত্য না: `buyer_name` জানলে `order_no` জানা যায় না, কারণ একটা Buyer-এর অনেক অর্ডার।

**চেনার প্রশ্ন:** "A-এর একটা মানের জন্য B-এর কি সবসময় একটাই মান থাকে?" হ্যাঁ হলে `A → B`।

এই ধারণাটা পরের তিন ক্লাসের ভিত্তি। সমস্যার মূল কারণটাও এখানে: **টেবিলে এমন কলাম আছে, যা Primary Key-র উপর নয়, অন্য কলামের উপর নির্ভর করে।** যেমন `buyer_country` নির্ভর করে `buyer_name`-এর উপর।

### Normalization

**Normalization** হলো টেবিল ভেঙে এমনভাবে সাজানো, যাতে Redundancy আর Anomaly কমে যায়। মূল কথা: **একটা তথ্য একটা জায়গাতেই থাকবে।**

ধাপগুলোকে বলে **Normal Form**:

| ধাপ | সংক্ষেপে নিয়ম | কবে |
|---|---|---|
| **1NF** | এক ঘরে এক মান, কোনো পুনরাবৃত্ত কলাম না | কাল |
| **2NF** | 1NF + পুরো Key-র উপর নির্ভর | পরশু |
| **3NF** | 2NF + শুধু Key-র উপর নির্ভর | ১ ডিসেম্বর |

ধাপগুলো ক্রমে আসে: 2NF হতে হলে আগে 1NF হতে হবে। **বাস্তবের ERP-তে সাধারণত 3NF পর্যন্ত করা হয়।**

### order_flat ভাঙলে কী হবে

```
BUYER ──< STYLE ──< ORDERS
```

| টেবিল | কলাম |
|---|---|
| `BUYER` | buyer_id, buyer_name, buyer_country |
| `STYLE` | style_id, style_no, style_name, buyer_id |
| `ORDERS` | order_id, order_no, order_date, style_id, order_qty, unit_price |

এবার মিলিয়ে দেখো:
- **Insert:** অর্ডার ছাড়াই `BUYER`-এ Walmart রাখা যাবে
- **Update:** H&M-এর দেশ এক রো-তে বদলালেই হবে
- **Delete:** অর্ডার মুছলেও Buyer আর স্টাইল থাকবে

তোমার সপ্তাহ ৩-এর `buyer`, `style`, `orders` টেবিলও এই একই গঠনে বানানো। অর্থাৎ Normalization-এর কাজ তুমি আগেই কিছুটা করেছ, এই সপ্তাহে শিখবে **কেন আর কোন নিয়মে**।

## ৬. হোমওয়ার্ক

<details>
<summary>হোমওয়ার্ক ২ ও ৩-এর সমাধান</summary>

**২:** নাম `EMPLOYEES`-এ থাকলে একই বিভাগের নাম প্রতিটা কর্মীর রো-তে লিখতে হতো। নাম বদলালে অনেক রো বদলাতে হতো, আর কর্মী ছাড়া বিভাগ রাখা যেত না। তাই নাম একবারই থাকে `DEPARTMENTS`-এ।

**৩:** A-এর একটা মান জানলে B-এর মান নিশ্চিতভাবে জানা যায়। উদাহরণ: `(supplier_id, item_id) → unit_price`, কারণ একটা জোড়ার একটাই দাম।

## সারাংশ

- এক টেবিলে সব রাখলে Redundancy আসে, আর তা থেকে Anomaly
- Insert Anomaly: এক তথ্য ছাড়া আরেকটা রাখা যায় না
- Update Anomaly: এক জায়গায় বদলালে অন্য জায়গায় পুরনো থাকে
- Delete Anomaly: মুছলে দরকারি তথ্যও হারায়
- `A → B`: A জানলে B জানা যায়
- Normalization টেবিল ভেঙে সমস্যাগুলো দূর করে: 1NF → 2NF → 3NF

**পরের ক্লাস:** 1NF (First Normal Form)।
