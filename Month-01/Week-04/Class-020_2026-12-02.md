## ১. Naming Convention (৪৫ মিনিট)

ERP-তে শত শত টেবিল থাকে, আর কয়েকজন ডেভেলপার একসাথে কাজ করে। সবাই এক নিয়মে নাম দিলে কোড পড়া সহজ হয়। **কোন নিয়ম নিচ্ছ, তার চেয়ে জরুরি হলো সব জায়গায় একই নিয়ম রাখা।**

> কোম্পানিতে আগে থেকে নিয়ম থাকলে সেটাই মানবে, নিজেরটা না।

### অবজেক্টের নাম

| অবজেক্ট | নিয়ম | উদাহরণ |
|---|---|---|
| টেবিল | বিষয়ের নাম, একবচন | `buyer`, `style`, `goods_receive` |
| Primary Key | `টেবিল_pk` | `buyer_pk` |
| Foreign Key | `child_parent_fk` | `style_buyer_fk` |
| Unique | `টেবিল_কলাম_uk` | `style_style_no_uk` |
| Check | `টেবিল_কলাম_ck` | `orders_qty_ck` |
| Not Null (নাম দিলে) | `টেবিল_কলাম_nn` | `test_unit_name_nn` |
| Sequence | `টেবিল_seq` | `buyer_seq` |
| View | `নাম_v` | `order_summary_v` |
| Index | `টেবিল_কলাম_idx` | `style_buyer_id_idx` |
| Trigger | `টেবিল_কাজ_trg` | `goods_receive_stock_trg` |
| Package | `নাম_pkg` | `stock_pkg` |

> Sequence, View, Index সপ্তাহ ১১-এ, Package সপ্তাহ ১৯-এ, Trigger সপ্তাহ ২০-এ শিখবে।

আমাদের `orders` একবচনের নিয়মের ব্যতিক্রম, কারণ `ORDER` Reserved word। চাইলে `sales_order` বা `customer_order` নাম দেওয়া যায়।

### কলামের নাম

| ধরন | নিয়ম | উদাহরণ |
|---|---|---|
| ID | `টেবিল_id`, সব জায়গায় একই নাম | `buyer_id` (`buyer` আর `style` দুই টেবিলেই) |
| তারিখ | `_date` | `order_date`, `ship_date` |
| তারিখ-সময় | `_on` বা `_at` | `created_on` |
| হ্যাঁ/না | `is_` | `is_active` |
| পরিমাণ | `_qty` | `order_qty` |
| টাকা | `_amount`, `_price` | `total_amount`, `unit_price` |
| শতকরা | `_pct` | `efficiency_pct` |
| কোড বা নম্বর | `_no`, `_code` | `style_no`, `emp_code` |
| বাংলা | `_bn` | `supplier_name_bn` |

**FK কলামের নাম Parent-এর PK-র মতোই রাখো।** `style.buyer_id` দেখলেই বোঝা যায় এটা `buyer.buyer_id`-এর দিকে গেছে। একই Parent-এ দুইটা FK হলে অর্থ বোঝাও: `requested_by_id`, `approved_by_id`।

### এড়িয়ে চলো

| খারাপ | সমস্যা | ভালো |
|---|---|---|
| `tbl_buyer`, `t_style` | `tbl_` কোনো তথ্য দেয় না | `buyer`, `style` |
| `Data1`, `info`, `temp` | কিসের তথ্য বোঝা যায় না | `shipment_note` |
| `q`, `amt2` | অস্পষ্ট | `order_qty`, `freight_amount` |
| `"Order Details"` | Double Quote, প্রতিবার হুবহু লিখতে হয় | `order_detail` |
| `date`, `size`, `order` | Reserved word | `ship_date`, `size_code` |
| একই জিনিসের কয়েক নাম | `qty`, `quantity`, `qnty` একসাথে | সব জায়গায় `qty` |

### মডিউল প্রিফিক্স

বড় ERP-তে একই Schema-তে টেবিলের নামের আগে মডিউলের প্রিফিক্স দেওয়া হয়। এতে টেবিলগুলো তালিকায় এক জায়গায় আসে, আর নাম মেলে না।

| প্রিফিক্স | মডিউল | উদাহরণ |
|---|---|---|
| `mrc_` | Merchandising | `mrc_buyer`, `mrc_style` |
| `inv_` | Inventory | `inv_item`, `inv_goods_receive` |
| `prd_` | Production | `prd_line`, `prd_hourly_output` |
| `lib_` | Library (আমাদের প্র্যাকটিস প্রজেক্ট) | `lib_book`, `lib_member` |

## ২. Data Type বাছাইয়ের নিয়ম (২০ মিনিট)

সপ্তাহ ২-এ শিখেছ। এখন সেটা নিয়ম আকারে:

| তথ্য | ঠিক | ভুল | কারণ |
|---|---|---|---|
| তারিখ | `DATE` | `VARCHAR2` | লেখায় রাখলে তুলনা আর হিসাব হয় না |
| টাকা | `NUMBER(12,2)` | `BINARY_DOUBLE` | টাকায় একদম সঠিক হিসাব লাগে |
| ফোন, NID | `VARCHAR2` | `NUMBER` | শুরুর 0 হারায় |
| বাংলা | `VARCHAR2(100 CHAR)` | `VARCHAR2(100)` | বাংলায় অক্ষরপ্রতি ৩ byte |
| Y/N | `CHAR(1)` + Check | `VARCHAR2(10)` | শুধু দুইটা মান |
| লম্বা লেখা | `VARCHAR2(4000)`, তারপর `CLOB` | শুরুতেই `CLOB` | `CLOB`-এ কাজ করা ধীর আর কঠিন |

**তারিখ `VARCHAR2`-এ রাখলে যা হয়:**

```sql
SELECT '15-01-2027' AS d FROM dual
UNION ALL
SELECT '02-12-2026' FROM dual
ORDER BY d;
```

লেখা হিসেবে সাজালে `02-12-2026` আগে, এখানে ঠিক এসেছে। কিন্তু `01-03-2027` আর `31-12-2026` তুলনা করলে `01-03-2027` আগে আসবে, যদিও এটা পরের তারিখ। (`UNION` সপ্তাহ ১০-এ, `ORDER BY` সপ্তাহ ৬-এ শিখবে।)

**সাইজ ঠিক রাখার নিয়ম:** পরিমাণের কলামে যথেষ্ট জায়গা রাখো (`NUMBER(12,3)`)। ডলারে ইউনিট প্রাইসে ৪ দশমিক (`NUMBER(10,4)`) লাগে। পরে কলাম বড় করা সহজ, ছোট করা কঠিন।

## ৩. Audit কলাম, Soft Delete, Lookup (২৫ মিনিট)

### Audit কলাম

ERP-তে প্রশ্ন আসেই: "এই রেকর্ড কে বানিয়েছে? কে শেষবার বদলেছে?" তাই প্রায় সব টেবিলে ৪টা কলাম রাখা হয়:

```sql
CREATE TABLE demo_buyer (
    buyer_id    NUMBER(10),
    buyer_name  VARCHAR2(100) NOT NULL,
    is_active   CHAR(1)       DEFAULT 'Y' NOT NULL,
    created_by  VARCHAR2(100) DEFAULT USER NOT NULL,
    created_on  DATE          DEFAULT SYSDATE NOT NULL,
    updated_by  VARCHAR2(100),
    updated_on  DATE,
    CONSTRAINT demo_buyer_pk PRIMARY KEY (buyer_id),
    CONSTRAINT demo_buyer_is_active_ck CHECK (is_active IN ('Y', 'N'))
);

INSERT INTO demo_buyer (buyer_id, buyer_name) VALUES (1, 'Primark');
COMMIT;

SELECT * FROM demo_buyer;
```

`created_by`-তে এখন ডাটাবেস ইউজার `LEARN` বসেছে। APEX অ্যাপে সবাই একই ডাটাবেস ইউজার দিয়ে চলে, তাই সেখানে অ্যাপের ইউজারের নাম Trigger দিয়ে বসানো হয় (`APEX` অংশে শিখবে)।

### Soft Delete

ERP-তে মাস্টার ডাটা সাধারণত মোছা হয় না। কারণ পুরনো লেনদেন সেটার উপর নির্ভর করে, আর FK-ও মুছতে দেয় না।

| পদ্ধতি | কী হয় |
|---|---|
| **Hard Delete** | `DELETE`, রেকর্ড চলে যায় |
| **Soft Delete** | `is_active = 'N'`, রেকর্ড থাকে, শুধু নতুন কাজে দেখায় না |

```sql
UPDATE demo_buyer SET is_active = 'N' WHERE buyer_id = 1;
ROLLBACK;
```

লেনদেনের রেকর্ড ভুল হলে মোছার বদলে সাধারণত `status = 'CANCELLED'` করা হয়, যাতে ইতিহাস থাকে।

### Check নাকি Lookup টেবিল

| | Check Constraint | Lookup টেবিল + FK |
|---|---|---|
| উদাহরণ | `is_active IN ('Y', 'N')` | `item_category` |
| নতুন মান যোগ করতে | টেবিল বদলাতে হয় (ডেভেলপার) | একটা `INSERT` (ইউজারও পারে) |
| বাড়তি তথ্য | রাখা যায় না | রাখা যায় |
| কখন | মান খুব কম, প্রায় বদলায় না | মান বাড়তে পারে, ইউজার যোগ করবে |

**নিয়ম:** Y/N, স্ট্যাটাস → Check। ক্যাটাগরি, দেশ, ইউনিট, রং, বিভাগ → Lookup টেবিল।

## ৪. ডাটাবেসেই ডকুমেন্ট (১৫ মিনিট)

টেবিল আর কলামের ব্যাখ্যা ডাটাবেসেই রাখা যায়:

```sql
COMMENT ON TABLE demo_buyer IS 'Buyer master for the demo module';
COMMENT ON COLUMN demo_buyer.is_active IS 'Y = usable in new orders, N = hidden';

SELECT table_name, comments
FROM   user_tab_comments
WHERE  table_name = 'DEMO_BUYER';

SELECT column_name, comments
FROM   user_col_comments
WHERE  table_name = 'DEMO_BUYER';
```

SQL Developer-এ টেবিল খুলে **Columns** ট্যাবে এই `COMMENTS` দেখা যায়। `learn` ইউজারের সব টেবিলের `CREATE` কোড `.sql` ফাইলে রাখবে, যাতে ডাটাবেস আবার বানানো যায়।

## ৫. ডিজাইন রিভিউ চেকলিস্ট (১৫ মিনিট)

নতুন ডিজাইন শেষ করে মিলিয়ে দেখো। **কাল টেস্টে এই তালিকা ধরে নিজের কাজ দেখবে।**

**টেবিল ও Key**
- [ ] প্রতিটা টেবিল একটাই বিষয়ের
- [ ] প্রতিটা টেবিলে Primary Key আছে
- [ ] বাস্তবে যেটা ইউনিক (`style_no`, ইমেইল), তাতে Unique আছে

**সম্পর্ক**
- [ ] প্রতিটা সম্পর্কে Foreign Key আছে
- [ ] FK Many দিকের টেবিলে
- [ ] M:N সম্পর্ক Junction Table দিয়ে ভাঙা
- [ ] ER Diagram আর টেবিল ডিজাইন মিলছে

**Normalization**
- [ ] এক ঘরে এক মান, `item1`, `item2` কলাম নেই (1NF)
- [ ] কোনো Partial Dependency নেই (2NF)
- [ ] কোনো Transitive Dependency নেই (3NF)
- [ ] ইচ্ছাকৃত Denormalization হলে কারণ লেখা আছে

**ডাটার মান**
- [ ] প্রয়োজনীয় কলামে Not Null
- [ ] পরিমাণ, স্ট্যাটাসে Check
- [ ] সঠিক Data Type: তারিখে `DATE`, ফোনে `VARCHAR2`, বাংলায় `CHAR`

**নাম ও ডকুমেন্ট**
- [ ] সব নাম এক নিয়মে, কোনো Reserved word বা Double Quote নেই
- [ ] সব Constraint-এর নিজের দেওয়া নাম
- [ ] দরকারি টেবিলে Audit কলাম

## ৬. হাতে-কলমে প্র্যাকটিস (৬০ মিনিট)

**কাজ ১:** এই ডিজাইনে কমপক্ষে ১০টা ভুল খুঁজে বের করো। এই কোড চালাবে না, শুধু পড়ো।

```sql
CREATE TABLE tblPurchase (
    ID          NUMBER,
    "PO Number" VARCHAR2(20),
    date1       VARCHAR2(20),
    Supplier    VARCHAR2(100),
    SupMobile   NUMBER,
    Item1       VARCHAR2(100),
    Qty1        NUMBER,
    Item2       VARCHAR2(100),
    Qty2        NUMBER,
    total       BINARY_DOUBLE,
    active      VARCHAR2(10)
);
```

**কাজ ২:** ডিজাইনটা ঠিক করে `learn_freepdb1`-এ বানাও। `d20_` প্রিফিক্স দাও, যাতে আগের টেবিলের সাথে নাম না মেলে। Audit কলাম আর `COMMENT ON` দাও। ডাটা ঢুকিয়ে দেখো।

**কাজ ৩:** নিজের `learn` স্কিমার Constraint-গুলো দেখো। নাম `SYS_C` দিয়ে শুরু হওয়া Not Null ছাড়া অন্য Constraint থাকলে তার তালিকা বানাও।

```sql
SELECT table_name, constraint_name, constraint_type
FROM   user_constraints
WHERE  constraint_name LIKE 'SYS\_C%' ESCAPE '\'
AND    constraint_type <> 'C'
ORDER  BY table_name;
```
