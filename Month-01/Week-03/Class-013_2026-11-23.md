# ক্লাস ১৩: Relationship: One-to-One ও One-to-Many

**তারিখ:** ২৩ নভেম্বর ২০২৬, সোমবার
**সময়:** সন্ধ্যা ৭:০০ থেকে রাত ১০:০০
**সপ্তাহ:** ৩ | **ধাপ:** ১ (কম্পিউটার ও ডাটাবেসের বেসিক)

---

## আজকে কী শিখব

- Relationship কী, কয় ধরনের
- কীভাবে বোঝা যায় কোনটা কোন Relationship
- One-to-Many: FK কোন টেবিলে বসবে
- One-to-One: FK আর Unique দিয়ে বানানো
- Optional আর Mandatory Relationship
- Self-Referencing Relationship

---

## ১. Relationship কী (২০ মিনিট)

**Relationship** হলো দুইটা টেবিলের ডাটার মধ্যে সম্পর্ক। গতকাল Foreign Key দিয়ে এই সম্পর্কই ডাটাবেসে বসানো শিখেছি।

| ধরন | মানে | উদাহরণ |
|---|---|---|
| **One-to-One (১:১)** | এক রো-র সাথে অন্য টেবিলের সর্বোচ্চ এক রো | এক কর্মীর একটা বেতনের রেকর্ড |
| **One-to-Many (১:N)** | এক রো-র সাথে অন্য টেবিলের অনেক রো | এক Buyer-এর অনেক স্টাইল |
| **Many-to-Many (M:N)** | দুই দিক থেকেই অনেক | এক সাপ্লায়ারের অনেক আইটেম, এক আইটেমের অনেক সাপ্লায়ার (কাল শিখব) |

### চেনার নিয়ম: দুই দিক থেকে প্রশ্ন করো

**"একটা A-এর কয়টা B?"** আর **"একটা B-এর কয়টা A?"**

| A আর B | একটা A-এর কয়টা B | একটা B-এর কয়টা A | ধরন |
|---|---|---|---|
| Buyer, Style | অনেক | ১ | ১:N |
| Worker, বেতনের রেকর্ড | ১ | ১ | ১:১ |
| Supplier, Item | অনেক | অনেক | M:N |

> উত্তর নির্ভর করে ব্যবসার নিয়মের উপর। একই স্টাইল দুই Buyer-কে দেওয়া হলে Buyer-Style আর ১:N থাকে না। তাই ডিজাইনের আগে ব্যবহারকারীর কাছে জেনে নিতে হয়।

## ২. One-to-Many (৫০ মিনিট)

ডাটাবেসে সবচেয়ে বেশি দেখা যায় এই সম্পর্ক। ERP-র প্রায় সব টেবিলই এভাবে যুক্ত।

```
BUYER ──< STYLE ──< ORDERS ──< ORDER_SIZE_QTY
```

`──<` মানে "একটার সাথে অনেকগুলো"। যেদিকে `<`, সেটা Many দিক।

### নিয়ম: FK সবসময় Many দিকের টেবিলে

| ডিজাইন | ঠিক/ভুল | কেন |
|---|---|---|
| `style` টেবিলে `buyer_id` | ✅ | প্রতিটা স্টাইলের একটাই Buyer, এক ঘরে এক মান |
| `buyer` টেবিলে `style_ids = '1,2,3'` | ❌ | এক সেলে অনেক মান, FK দেওয়া যায় না |
| `buyer` টেবিলে `style_1`, `style_2`, `style_3` | ❌ | ৪টা স্টাইল হলে কলাম বাড়াতে হবে |

### ডাটায় দেখো

ক্লাস ১১ আর ১২-এর টেবিলগুলোতে এই সম্পর্ক আছে:

```sql
-- H&M-এর সব স্টাইল
SELECT style_id, style_no, style_name
FROM   style
WHERE  buyer_id = 1;

-- স্টাইল 1-এর সব অর্ডার
SELECT order_no, order_qty, status
FROM   orders
WHERE  style_id = 1;
```

### পরের ধাপটা যুক্ত করো

ক্লাস ১১-এর `order_size_qty` টেবিল এখনো `orders`-এর সাথে যুক্ত নয়। এখানে যোগসূত্র `order_no`, যেটা `orders` টেবিলে Unique:

```sql
ALTER TABLE order_size_qty ADD CONSTRAINT order_size_qty_order_fk
    FOREIGN KEY (order_no) REFERENCES orders (order_no);

-- এমন অর্ডার নেই, তাই এরর ORA-02291
INSERT INTO order_size_qty VALUES ('ORD-999', 'Black', 'S', 100);
```

মনে করো, FK Parent-এর **PK বা Unique** যেকোনোটার দিকে যেতে পারে।

### দুই টেবিলের ডাটা একসাথে (শুধু দেখো)

```sql
SELECT b.buyer_name, s.style_no, s.style_name
FROM   buyer b
JOIN   style s ON s.buyer_id = b.buyer_id;
```

এটাকে বলে **JOIN**। সপ্তাহ ৯-এ বিস্তারিত শিখব। এখন শুধু দেখো, নাম একবার লিখেও প্রতিটা স্টাইলের পাশে Buyer-এর নাম পাওয়া যাচ্ছে।

## ৩. One-to-One (৪০ মিনিট)

এক রো-র সাথে অন্য টেবিলের **সর্বোচ্চ এক রো**।

**প্রশ্ন:** তাহলে একই টেবিলে রাখলেই তো হয়?

সাধারণত তা-ই করা উচিত। আলাদা টেবিল তখনই, যখন:

| কারণ | উদাহরণ |
|---|---|
| গোপন ডাটা আলাদা অনুমতিতে রাখা | কর্মীর তথ্য সবাই দেখবে, বেতন শুধু HR |
| বড় ফাইল আলাদা রাখা | স্টাইলের তথ্য আর তার ছবি (BLOB) |
| সবার জন্য প্রযোজ্য না | শুধু কিছু কর্মীর ব্যাংক অ্যাকাউন্ট আছে |

### উপায় ১: PK-ই FK

```sql
CREATE TABLE worker_salary (
    worker_id     NUMBER(10),
    basic_salary  NUMBER(10,2) NOT NULL,
    CONSTRAINT worker_salary_pk PRIMARY KEY (worker_id),
    CONSTRAINT worker_salary_worker_fk FOREIGN KEY (worker_id) REFERENCES worker (worker_id)
);

INSERT INTO worker_salary VALUES (1, 18500);
INSERT INTO worker_salary VALUES (2, 15200);
COMMIT;

-- একই কর্মীর দ্বিতীয় রেকর্ড, তাই এরর ORA-00001
INSERT INTO worker_salary VALUES (1, 20000);

-- এমন কর্মী নেই, তাই এরর ORA-02291
INSERT INTO worker_salary VALUES (99, 10000);
```

### উপায় ২: নিজের ID, আর FK-তে Unique

```sql
CREATE TABLE worker_bank (
    bank_info_id  NUMBER(10),
    worker_id     NUMBER(10)   NOT NULL,
    bank_name     VARCHAR2(100),
    account_no    VARCHAR2(30),
    CONSTRAINT worker_bank_pk PRIMARY KEY (bank_info_id),
    CONSTRAINT worker_bank_worker_fk FOREIGN KEY (worker_id) REFERENCES worker (worker_id),
    CONSTRAINT worker_bank_worker_uk UNIQUE (worker_id)
);

INSERT INTO worker_bank VALUES (1, 1, 'Sample Bank', '0011223344');
COMMIT;

-- একই কর্মীর দ্বিতীয় অ্যাকাউন্ট, তাই এরর ORA-00001
INSERT INTO worker_bank VALUES (2, 1, 'Other Bank', '5566778899');
```

**সবচেয়ে জরুরি কথা:**

```
FK একা          = One-to-Many
FK + Unique     = One-to-One
```

`worker_bank_worker_uk` বাদ দিলে একজন কর্মীর অনেক অ্যাকাউন্ট রাখা যাবে, মানে সম্পর্কটা ১:N হয়ে যাবে। সম্পর্কের ধরন ঠিক হয় এই Constraint দিয়েই।

## ৪. Optional, Mandatory ও Self-Referencing (১৫ মিনিট)

### Optional আর Mandatory

| ধরন | মানে | কীভাবে বানায় |
|---|---|---|
| **Mandatory** | Parent ছাড়া Child থাকতে পারবে না | FK কলামে Not Null |
| **Optional** | Parent ছাড়াও Child থাকতে পারে | FK কলাম NULL রাখা যায় |

- প্রতিটা অর্ডারে স্টাইল থাকতেই হবে: `orders.style_id` **Not Null**
- নতুন কর্মীকে হয়তো এখনো লাইন দেওয়া হয়নি: `line_id` **NULL চলবে**

### Self-Referencing

কখনো একটা টেবিল **নিজের সাথেই** সম্পর্কিত। যেমন: একজন কর্মীর সুপারভাইজারও একজন কর্মী।

```sql
CREATE TABLE staff (
    staff_id       NUMBER(10),
    staff_name     VARCHAR2(100) NOT NULL,
    supervisor_id  NUMBER(10),
    CONSTRAINT staff_pk PRIMARY KEY (staff_id),
    CONSTRAINT staff_supervisor_fk FOREIGN KEY (supervisor_id) REFERENCES staff (staff_id)
);

INSERT INTO staff VALUES (1, 'Factory Manager', NULL);
INSERT INTO staff VALUES (2, 'Floor In-charge', 1);
INSERT INTO staff VALUES (3, 'Line Supervisor', 2);
COMMIT;
```

সবার উপরের জনের সুপারভাইজার নেই, তাই FK-তে NULL। HR স্কিমার `employees.manager_id` ঠিক এরকম। এ ধরনের ডাটা পড়া শিখব সপ্তাহ ৯ (Self Join) আর সপ্তাহ ১৩-এ (Hierarchical Query)।

## ৫. Relationship খুঁজে দেখা (১৫ মিনিট)

কোন টেবিল কোনটার Child, Data Dictionary থেকে দেখো:

```sql
SELECT c.table_name  AS child_table,
       c.constraint_name AS fk_name,
       p.table_name  AS parent_table
FROM   user_constraints c
JOIN   user_constraints p ON p.constraint_name = c.r_constraint_name
WHERE  c.constraint_type = 'R'
ORDER  BY p.table_name, c.table_name;
```

এই কোয়েরির পুরোটা এখনই বোঝার দরকার নেই। নিজের ফাইলে রেখে দাও। অচেনা ডাটাবেসে কাজ শুরু করলে এটা খুব কাজে লাগে।

HR স্কিমায় `hr_freepdb1` কানেকশনে চালিয়ে দেখো, ক্লাস ৯-এর ডায়াগ্রামের সাথে মেলে কি না।

## ৬. হাতে-কলমে প্র্যাকটিস (৪০ মিনিট)

**কাজ ১:** প্রতিটা জোড়ার সম্পর্কের ধরন লেখো, আর ১:N হলে FK কোন টেবিলে বসবে বলো।

1. Floor আর Sewing Line (একটা ফ্লোরে অনেক লাইন)
2. Order আর Shipment (একটা অর্ডার কয়েক চালানে যেতে পারে, প্রতিটা চালান একটা অর্ডারের)
3. Style আর Style Costing Sheet (প্রতিটা স্টাইলের একটাই কস্টিং শীট)
4. Item Category আর Item
5. Worker আর Sewing Line (একজন একটা লাইনে কাজ করে)
6. Item আর Unit of Measure (প্রতিটা আইটেমের একটাই ইউনিট)

**কাজ ২:** ১:N বানাও। `factory_floor` (floor_id, floor_name) আর `prod_line` (line_id, line_name, floor_id, daily_target)। নিয়ম:
- প্রতিটা লাইন অবশ্যই একটা ফ্লোরে থাকবে
- লাইনের নাম একই হবে না
- টার্গেট ০-এর বেশি

৩টা ফ্লোর আর ৫টা লাইন ঢোকাও। তারপর এমন ফ্লোর দিয়ে লাইন ঢোকানোর চেষ্টা করো, যা নেই।

**কাজ ৩:** ১:১ বানাও। `style_costing` টেবিল: style_id, fabric_cost, trim_cost, cm_cost। একটা স্টাইলের একটাই কস্টিং থাকবে। ২টা ডাটা ঢুকিয়ে একই স্টাইলে দ্বিতীয়বার চেষ্টা করো।

> **CM (Cost of Making):** একটা পোশাক সেলাই করে তৈরির খরচ। ধাপ ৮-এ বিস্তারিত।

|---|---|---|
| Floor, Sewing Line | ১:N | Sewing Line |
| Order, Shipment | ১:N | Shipment |
| Style, Costing Sheet | ১:১ | Costing Sheet (Unique সহ) |
| Category, Item | ১:N | Item |
| Sewing Line, Worker | ১:N | Worker |
| Unit, Item | ১:N | Item |

## ৭. হোমওয়ার্ক

1. তোমার পরিচিত কোনো দোকান বা অফিস থেকে ২টা ১:১ আর ৩টা ১:N সম্পর্কের উদাহরণ লেখো।
2. `worker` টেবিলে `line_id` কলাম যোগ করে `prod_line`-এর সাথে Optional ১:N সম্পর্ক বানাও। একজন কর্মীকে লাইনে দাও, আরেকজনকে খালি রাখো।
3. `BUYER → STYLE → ORDERS → ORDER_SIZE_QTY` চেইনটা খাতায় আঁকো। প্রতিটা টেবিলে PK, FK চিহ্নিত করো।

<details>
<summary>হোমওয়ার্ক ২-এর সমাধান</summary>

```sql
ALTER TABLE worker ADD (line_id NUMBER(5));

ALTER TABLE worker ADD CONSTRAINT worker_line_fk
    FOREIGN KEY (line_id) REFERENCES prod_line (line_id);

UPDATE worker SET line_id = 1 WHERE worker_id = 1;
COMMIT;

SELECT worker_id, emp_code, line_id FROM worker;
```

`line_id`-তে Not Null দিইনি, তাই বাকিদের এটা খালি থাকতে পারে। এটাই Optional সম্পর্ক। `UPDATE` বিস্তারিত সপ্তাহ ৫-এ।

</details>

2. Many দিকের টেবিলে
3. Unique Constraint (অথবা FK কলামটাকেই PK করা)
4. FK কলামে Not Null থাকে না, তাই NULL রাখা যায়
5. কর্মী আর তার সুপারভাইজার, দুজনই একই টেবিলে

</details>

## সারাংশ

- সম্পর্ক চিনতে দুই দিক থেকেই প্রশ্ন করো: একটা A-এর কয়টা B, একটা B-এর কয়টা A
- ১:N: FK Many দিকে
- ১:১: FK + Unique, বা PK-ই FK
- FK-তে Not Null থাকলে Mandatory, না থাকলে Optional
- একটা টেবিল নিজের সাথেও সম্পর্কিত হতে পারে

**পরের ক্লাস:** Many-to-Many ও Junction Table।
