## ১. Transaction কী (৩০ মিনিট)

**Transaction** হলো কয়েকটা DML-এর একটা দল, যা **একসাথে হবে, অথবা কোনোটাই হবে না।**

### উদাহরণ: মাল গ্রহণ

Store-এ ১০০ কেজি কাপড় এলো। দুইটা কাজ হয়:
1. `w5_receive` টেবিলে রিসিভের রো ঢোকানো
2. `w5_stock` টেবিলে স্টক ১০০ বাড়ানো

প্রথমটা হওয়ার পর দ্বিতীয়টার আগে কারেন্ট চলে গেলে? রিসিভের রেকর্ড আছে, কিন্তু স্টক বাড়েনি। হিসাব মিলবে না।

Transaction থাকায়: **শেষ না হওয়া কাজ ডাটাবেস নিজে থেকে বাতিল করে দেয়।**

### ACID

একটা ভালো Transaction-এর ৪টা বৈশিষ্ট্য। ইন্টারভিউতে প্রায়ই আসে।

| বৈশিষ্ট্য | মানে | উদাহরণ |
|---|---|---|
| **A**tomicity | সব হবে, অথবা কিছুই না | রিসিভ আর স্টক দুটোই, বা কোনোটাই না |
| **C**onsistency | নিয়ম কখনো ভাঙবে না | Constraint সবসময় মানা হবে |
| **I**solation | এক Transaction আরেকটার অসম্পূর্ণ কাজ দেখে না | তোমার না-COMMIT করা ডাটা আমি দেখি না |
| **D**urability | `COMMIT` হলে স্থায়ী | কারেন্ট গেলেও থাকবে |

### Transaction কখন শুরু আর শেষ

```
শুরু: প্রথম DML (INSERT, UPDATE, DELETE)
      │
      │  আরো DML ...
      ▼
শেষ:  COMMIT, ROLLBACK, অথবা কোনো DDL/DCL
```

Oracle-এ `BEGIN TRANSACTION` জাতীয় কিছু লিখতে হয় না।

### আজকের টেবিল

```sql
CREATE TABLE w5_stock (
    item_id      NUMBER(10),
    item_name    VARCHAR2(100) NOT NULL,
    balance_qty  NUMBER(12,3) DEFAULT 0 NOT NULL,
    CONSTRAINT w5_stock_pk PRIMARY KEY (item_id),
    CONSTRAINT w5_stock_balance_ck CHECK (balance_qty >= 0)
);

CREATE TABLE w5_receive (
    receive_id    NUMBER(10),
    item_id       NUMBER(10)   NOT NULL,
    receive_date  DATE         DEFAULT SYSDATE NOT NULL,
    qty           NUMBER(12,3) NOT NULL,
    CONSTRAINT w5_receive_pk PRIMARY KEY (receive_id),
    CONSTRAINT w5_receive_item_fk FOREIGN KEY (item_id) REFERENCES w5_stock (item_id),
    CONSTRAINT w5_receive_qty_ck CHECK (qty > 0)
);

INSERT INTO w5_stock (item_id, item_name, balance_qty) VALUES (1, 'Single Jersey', 500);
INSERT INTO w5_stock (item_id, item_name, balance_qty) VALUES (2, 'Pique', 200);
COMMIT;
```

## ২. COMMIT আর ROLLBACK (৩০ মিনিট)

| কমান্ড | কাজ |
|---|---|
| `COMMIT` | Transaction-এর সব পরিবর্তন স্থায়ী করে, সবাই দেখতে পায় |
| `ROLLBACK` | শেষ `COMMIT`-এর পরের সব পরিবর্তন বাতিল করে |

### সফল Transaction

```sql
INSERT INTO w5_receive (receive_id, item_id, qty) VALUES (1, 1, 100);

UPDATE w5_stock SET balance_qty = balance_qty + 100 WHERE item_id = 1;

SELECT * FROM w5_stock;
COMMIT;
```

### মাঝপথে সমস্যা

```sql
INSERT INTO w5_receive (receive_id, item_id, qty) VALUES (2, 2, 50);

-- ভুল করে item_id 1-এর স্টক বাড়ালাম
UPDATE w5_stock SET balance_qty = balance_qty + 50 WHERE item_id = 1;

SELECT * FROM w5_stock;
SELECT * FROM w5_receive;

ROLLBACK;

SELECT * FROM w5_stock;      -- আগের মতো
SELECT * FROM w5_receive;    -- রিসিভ ২ নেই
```

দুইটা কাজই বাতিল হলো। হিসাব ঠিক থাকল।

### একটা স্টেটমেন্ট ফেল করলে?

```sql
INSERT INTO w5_receive (receive_id, item_id, qty) VALUES (3, 1, 10);    -- চলবে
INSERT INTO w5_receive (receive_id, item_id, qty) VALUES (4, 99, 10);   -- এরর ORA-02291

SELECT * FROM w5_receive;    -- রিসিভ ৩ এখনো আছে
ROLLBACK;
```

**শুধু ফেল করা স্টেটমেন্ট বাতিল হয়, পুরো Transaction না।** এরপর কী করবে, `COMMIT` না `ROLLBACK`, সেটা তোমার সিদ্ধান্ত। লজিক ঠিক রাখতে এরকম ক্ষেত্রে সাধারণত পুরোটা `ROLLBACK` করা হয়। PL/SQL-এ এটা Exception Handling দিয়ে করব (সপ্তাহ ১৭)।

## ৩. SAVEPOINT (২৫ মিনিট)

**SAVEPOINT** হলো Transaction-এর ভেতরে একটা চিহ্ন। পুরোটা বাতিল না করে ওই চিহ্ন পর্যন্ত ফেরা যায়।

একটা একটা করে চালাও, আর প্রতিবার ফল দেখো:

```sql
UPDATE w5_stock SET balance_qty = 1000 WHERE item_id = 1;

SAVEPOINT after_first;

UPDATE w5_stock SET balance_qty = 2000 WHERE item_id = 1;

SAVEPOINT after_second;

UPDATE w5_stock SET balance_qty = 3000 WHERE item_id = 1;

SELECT balance_qty FROM w5_stock WHERE item_id = 1;   -- 3000

ROLLBACK TO after_second;
SELECT balance_qty FROM w5_stock WHERE item_id = 1;   -- 2000

ROLLBACK TO after_first;
SELECT balance_qty FROM w5_stock WHERE item_id = 1;   -- 1000

ROLLBACK;
SELECT balance_qty FROM w5_stock WHERE item_id = 1;   -- শেষ COMMIT-এর মান, 600
```

```
COMMIT ── UPDATE ── after_first ── UPDATE ── after_second ── UPDATE
  ▲                     ▲                        ▲
  │                     │                        └─ ROLLBACK TO after_second
  │                     └─ ROLLBACK TO after_first
  └─ ROLLBACK
```

### নিয়ম

- `ROLLBACK TO` Transaction শেষ করে না, চলতে থাকে। পরে `COMMIT` বা `ROLLBACK` দিতে হয়
- `ROLLBACK TO after_first` করলে তার পরের সেভপয়েন্ট (`after_second`) আর থাকে না
- `COMMIT` বা পুরো `ROLLBACK`-এর পরে সব সেভপয়েন্ট চলে যায়

```sql
ROLLBACK TO after_first;
```

```
ORA-01086: savepoint 'AFTER_FIRST' never established in this session or is invalid
```

**কোথায় কাজে লাগে:** একটা বড় কাজের কোনো অংশ ফেল করলে শুধু সেই অংশ বাতিল করে বাকিটা রাখা। যেমন ১০টা আইটেমের মধ্যে ১টা না মিললে।

## ৪. নিজে থেকে COMMIT ও ROLLBACK (২০ মিনিট)

| ঘটনা | কী হয় |
|---|---|
| **DDL বা DCL চালালে** (`CREATE`, `ALTER`, `DROP`, `TRUNCATE`, `GRANT`) | আগের সব পরিবর্তন **COMMIT** |
| SQL*Plus-এ `EXIT` দিয়ে বের হলে | **COMMIT** (ডিফল্ট) |
| SQL Developer বন্ধ করলে | জিজ্ঞেস করে: Commit না Rollback |
| সেশন হঠাৎ বন্ধ, কম্পিউটার বন্ধ, নেটওয়ার্ক গেলে | **ROLLBACK** |

### DDL-এর ফাঁদ নিজে দেখো

```sql
UPDATE w5_stock SET balance_qty = 99999 WHERE item_id = 2;

-- একদম অন্য একটা টেবিল বানালাম
CREATE TABLE w5_temp (id NUMBER);

ROLLBACK;

SELECT * FROM w5_stock;      -- 99999 রয়ে গেছে! ফেরানো যায়নি
```

`CREATE TABLE`-এর সাথে সাথে `UPDATE` স্থায়ী হয়ে গেছে। এটা ঠিক করে নাও:

```sql
UPDATE w5_stock SET balance_qty = 200 WHERE item_id = 2;
COMMIT;

DROP TABLE w5_temp;
```

**নিয়ম:** ডাটা বদলানো আর গঠন বদলানো এক সাথে করবে না। আগে `COMMIT` বা `ROLLBACK`, তারপর DDL।

### Autocommit

SQL Developer-এ **Tools → Preferences → Database → Advanced → Autocommit** আছে। এটা **বন্ধ রাখো।** চালু থাকলে প্রতিটা DML সাথে সাথে স্থায়ী হয়, ভুল ফেরানোর সুযোগ থাকে না।

> **APEX-এ:** পেজ সাবমিট হওয়ার পর সব Process শেষ হলে APEX নিজে থেকে `COMMIT` করে, আর এরর হলে `ROLLBACK`। তাই APEX-এর Process-এ সাধারণত `COMMIT` লিখতে হয় না। সপ্তাহ ২৯-এ দেখবে।

## ৫. দুই সেশন: কে কী দেখে, Lock (২৫ মিনিট)

দুইটা আলাদা সেশন খোলো:
- **সেশন A:** SQL Developer-এর `learn_freepdb1`
- **সেশন B:** cmd-তে `sqlplus learn/Learn123@localhost:1521/FREEPDB1`

### পরীক্ষা ১: না-COMMIT করা ডাটা অন্যে দেখে না

| ধাপ | সেশন A (SQL Developer) | সেশন B (SQL*Plus) |
|---|---|---|
| ১ | `UPDATE w5_stock SET balance_qty = 777 WHERE item_id = 2;` | |
| ২ | `SELECT balance_qty FROM w5_stock WHERE item_id = 2;` → **777** | `SELECT balance_qty FROM w5_stock WHERE item_id = 2;` → **200** |
| ৩ | `COMMIT;` | |
| ৪ | | আবার `SELECT` → **777** |

এটাই Isolation। সেশন A নিজের কাজ দেখে, B শুধু `COMMIT` হওয়া ডাটা দেখে। Oracle-এ পড়ার জন্য কেউ আটকায় না।

### পরীক্ষা ২: Lock

একই রো দুইজন একসাথে বদলাতে পারে না।

| ধাপ | সেশন A | সেশন B |
|---|---|---|
| ১ | `UPDATE w5_stock SET balance_qty = 300 WHERE item_id = 2;` | |
| ২ | | `UPDATE w5_stock SET balance_qty = 400 WHERE item_id = 2;` → **আটকে আছে, কিছু দেখাচ্ছে না** |
| ৩ | `COMMIT;` | সাথে সাথে `1 row updated.` |
| ৪ | | `ROLLBACK;` |

- **Lock:** A যে রো বদলাচ্ছে, সেটা `COMMIT` বা `ROLLBACK` পর্যন্ত আটকে থাকে
- অন্য রো বদলাতে কোনো বাধা নেই (Row-level Lock)
- শেষে `SELECT` করলে মান `300` দেখাবে, কারণ B-র কাজ বাতিল হয়েছে

**বাস্তব শিক্ষা:** কেউ `UPDATE` করে `COMMIT` না দিয়ে চা খেতে গেলে অন্যরা আটকে থাকে। তাই Transaction ছোট রাখো, কাজ শেষে সাথে সাথে `COMMIT`।

> **Deadlock:** A আটকে আছে B-র জন্য, আর B আটকে আছে A-র জন্য। Oracle নিজে ধরে ফেলে, একটাকে `ORA-00060` দিয়ে থামায়।

কাজ শেষে SQL*Plus-এ `exit` দাও।

## ৬. হাতে-কলমে প্র্যাকটিস (৫০ মিনিট)

**কাজ ১:** চালানোর আগে আন্দাজ করো, শেষে `w5_stock`-এ `item_id = 1`-এর `balance_qty` কত থাকবে? প্রতিটা আলাদাভাবে করো। আগে `UPDATE w5_stock SET balance_qty = 100 WHERE item_id = 1; COMMIT;` চালিয়ে নাও।

**ক.**
```sql
UPDATE w5_stock SET balance_qty = 200 WHERE item_id = 1;
COMMIT;
UPDATE w5_stock SET balance_qty = 300 WHERE item_id = 1;
ROLLBACK;
```

**খ.**
```sql
UPDATE w5_stock SET balance_qty = 200 WHERE item_id = 1;
SAVEPOINT s1;
UPDATE w5_stock SET balance_qty = 300 WHERE item_id = 1;
ROLLBACK TO s1;
COMMIT;
```

**গ.**
```sql
UPDATE w5_stock SET balance_qty = 400 WHERE item_id = 1;
CREATE TABLE w5_t1 (id NUMBER);
ROLLBACK;
DROP TABLE w5_t1;
```

**ঘ.**
```sql
UPDATE w5_stock SET balance_qty = 500 WHERE item_id = 1;
UPDATE w5_stock SET balance_qty = -1 WHERE item_id = 1;
COMMIT;
```

**কাজ ২:** মাল প্রদান (Issue)-এর Transaction লেখো: ৫০ কেজি Single Jersey কাটিং-এ গেল। `w5_issue` টেবিল বানাও (issue_id, item_id, qty, issue_date)। তারপর `w5_issue`-তে রো আর `w5_stock`-এ স্টক কমানো, দুইটা একসাথে করে `COMMIT` দাও।

**কাজ ৩:** স্টকের চেয়ে বেশি পরিমাণ ইস্যু করার চেষ্টা করো (যেমন ১০০০০ কেজি)। `w5_issue`-তে রো ঢুকবে, কিন্তু স্টকের `UPDATE`-এ Check `ORA-02290` দেবে। এখন কী করবে, আর কেন? সেই কমান্ড চালাও।

**কাজ ৪:** `SAVEPOINT` দিয়ে ৩ আইটেমের রিসিভ করো। আইটেম ১ আর ২-এর পরে সেভপয়েন্ট দাও। আইটেম ৩-এ ভুল পরিমাণ দিয়েছ বুঝে শুধু সেটা বাতিল করো, আর বাকি ২টা `COMMIT` করো। (`w5_stock`-এ ৩ নম্বর আইটেম `Rib` যোগ করে নাও।)

## সারাংশ

- Transaction: সব হবে, অথবা কিছুই না
- `COMMIT` স্থায়ী, `ROLLBACK` শেষ `COMMIT` পর্যন্ত বাতিল, `SAVEPOINT` মাঝের চিহ্ন
- DDL আর DCL নিজে থেকে `COMMIT` করে
- এক স্টেটমেন্ট ফেল করলে শুধু সেটাই বাতিল, বাকি সিদ্ধান্ত তোমার
- না-COMMIT করা ডাটা অন্যে দেখে না, আর বদলানো রো Lock থাকে। তাই Transaction ছোট রাখো
