**তারিখ:** ১৭ জানুয়ারি ২০২৭, রবিবার

## আজকে কী শিখব

- Materialized View কী, কেন লাগে

## ১. কেন লাগে (২০ মিনিট)

কালকের View-তে ডাটা নেই। প্রতিবার ভেতরের কোয়েরি চলে। ম্যানেজমেন্টের ড্যাশবোর্ডে ১০ বছরের ডাটার হিসাব থাকলে?

```
১০ লাখ রো × ৫ টেবিলের JOIN × GROUP BY = ৩০ সেকেন্ড
৫০ জন একসাথে খুললে ডাটাবেসের উপর চাপ
```

**Materialized View (MV)** কোয়েরির **ফল** টেবিলের মতো জমা রাখে। পড়া খুব দ্রুত।

```
View              = কোয়েরি জমা, প্রতিবার চলে, ফল টাটকা
Materialized View = ফল জমা, পড়া দ্রুত, ফল পুরনো হতে পারে
```

ক্লাস ১৯-এ "Denormalization" শিখেছিলে: হিসাবের ফল জমা রাখা। MV-তে Oracle নিজে সেই জমা রাখা আর আপডেটের দায়িত্ব নেয়।

### কোথায় লাগে

| ব্যবহার | কেন |
|---|---|
| ড্যাশবোর্ড | এক ঘণ্টা পুরনো ডাটায় সমস্যা নেই, দ্রুত খোলে |
| মাসিক রিপোর্ট | পুরনো মাসের ডাটা বদলায় না |
| অন্য ডাটাবেসের কপি | নেটওয়ার্ক কম লাগে (সপ্তাহ ৩৯) |

## ২. MV বানানো (৪০ মিনিট)

```sql
CREATE MATERIALIZED VIEW lib_category_issue_mv
BUILD IMMEDIATE
REFRESH COMPLETE ON DEMAND
AS
SELECT cat.category_name, COUNT(*) AS issues
FROM   lib_book_issue i
JOIN   lib_book_copy c  ON i.copy_id = c.copy_id
JOIN   lib_book b       ON c.book_id = b.book_id
JOIN   lib_category cat ON b.category_id = cat.category_id
GROUP  BY cat.category_name;

-- Database 11, Programming 6, Novel 4
SELECT * FROM lib_category_issue_mv ORDER BY issues DESC;
```

| অংশ | মানে |
|---|---|
| `BUILD IMMEDIATE` | এখনই ডাটা ভরো (ডিফল্ট) |
| `BUILD DEFERRED` | প্রথম Refresh-এ ভরো |
| `REFRESH COMPLETE` | পুরো কোয়েরি আবার চালিয়ে ভরো |
| `ON DEMAND` | আমি বললে Refresh হবে |

### MV পুরনো হয়ে যায়

```sql
-- নতুন একটা ইস্যু: কপি ১৭, বই ১২, History ক্যাটাগরি
INSERT INTO lib_book_issue (issue_id, copy_id, member_id, staff_id, due_date)
VALUES (900, 17, 1, 1, TRUNC(SYSDATE) + 14);
COMMIT;

-- MV-তে History নেই
SELECT * FROM lib_category_issue_mv ORDER BY issues DESC;

-- আসল কোয়েরিতে History 1
SELECT cat.category_name, COUNT(*) AS issues
FROM   lib_book_issue i
JOIN   lib_book_copy c  ON i.copy_id = c.copy_id
JOIN   lib_book b       ON c.book_id = b.book_id
JOIN   lib_category cat ON b.category_id = cat.category_id
GROUP  BY cat.category_name
ORDER  BY issues DESC;
```

### Refresh

```sql
EXEC DBMS_MVIEW.REFRESH('LIB_CATEGORY_ISSUE_MV', 'C');

-- এবার History 1
SELECT * FROM lib_category_issue_mv ORDER BY issues DESC;
```

`'C'` মানে Complete। `EXEC` একটা PL/SQL প্রসিডিওর চালায় (সপ্তাহ ১৮)। `F5` বা `Ctrl + Enter` দুই দিয়েই চলে।

### পরীক্ষার ডাটা সরিয়ে নাও

সামনের ক্লাসের সংখ্যা ঠিক রাখতে:

```sql
DELETE FROM lib_book_issue WHERE issue_id = 900;
COMMIT;

EXEC DBMS_MVIEW.REFRESH('LIB_CATEGORY_ISSUE_MV', 'C');
```

### MV কেমন

```sql
SELECT mview_name, refresh_mode, refresh_method, last_refresh_date, staleness
FROM   user_mviews;
```

`staleness`: `FRESH` মানে আসল ডাটার সাথে মিলছে, `STALE` মানে পুরনো। আসল টেবিল বদলের পরে `NEEDS_COMPILE`-ও দেখাতে পারে, সেটাও মানে Refresh লাগবে।

MV-র উপর Index বানানো যায়, কারণ এটা আসলে টেবিলের মতো জমা থাকে:

```sql
CREATE INDEX lib_category_issue_mv_idx ON lib_category_issue_mv (category_name);
```

## ৩. Refresh-এর ধরন (৩৫ মিনিট)

Refresh দুইটা প্রশ্নের উত্তর: **কীভাবে** আর **কখন**।

### কীভাবে

| পদ্ধতি | কাজ | গতি |
|---|---|---|
| `COMPLETE` | পুরো ফল আবার হিসাব | বড় ডাটায় ধীর |
| `FAST` | শুধু বদলানো রো | দ্রুত, তবে MV Log লাগে |
| `FORCE` | পারলে `FAST`, নাহলে `COMPLETE` | ডিফল্ট |

### কখন

| সময় | কাজ | ব্যবহার |
|---|---|---|
| `ON DEMAND` | আমি বললে | রাতে Job দিয়ে |
| `ON COMMIT` | আসল টেবিলে `COMMIT`-এর সাথে সাথে | ছোট, কম লেনদেনের টেবিল |
| `NEXT` | নির্দিষ্ট সময় পরপর | প্রতি ঘণ্টায় |

**বাস্তবে সবচেয়ে বেশি:** `COMPLETE ON DEMAND`, আর রাতে Scheduler Job দিয়ে Refresh। `DBMS_SCHEDULER` সপ্তাহ ২২-এ শিখবে।

### Refresh-এর সময়সূচি দিয়ে

```sql
CREATE MATERIALIZED VIEW lib_daily_count_mv
BUILD IMMEDIATE
REFRESH COMPLETE
START WITH SYSDATE
NEXT TRUNC(SYSDATE) + 1 + 1/24
AS
SELECT COUNT(*) AS total_issues FROM lib_book_issue;

DROP MATERIALIZED VIEW lib_daily_count_mv;
```

প্রতিদিন রাত ১টায় Refresh হবে। এর জন্য Job চালানোর অনুমতি লাগতে পারে, এরর এলে এখন বাদ দাও। সপ্তাহ ২২-এ Scheduler দিয়ে করবে।

### কয়েকটা MV একসাথে

```sql
EXEC DBMS_MVIEW.REFRESH('LIB_CATEGORY_ISSUE_MV', 'C');
```

কমা দিয়ে কয়েকটা নাম একসাথে দেওয়া যায়: `'MV1,MV2'`।

### Refresh-এর সময়টাও চিন্তার বিষয়

`COMPLETE` Refresh চলাকালে ডাটাবেসে চাপ পড়ে। তাই কাজের সময়ের বাইরে করা হয়। ব্যবহারকারীকে জানিয়ে রাখো: "ড্যাশবোর্ডের ডাটা গত রাত পর্যন্ত।" পেজে `last_refresh_date` দেখানো ভালো অভ্যাস।

## ৪. FAST Refresh ও MV Log (২৫ মিনিট)

`FAST` Refresh-এর জন্য আসল টেবিলে **MV Log** লাগে। এটা একটা ছোট টেবিল, যেখানে Oracle বদলানো রো টুকে রাখে।

```sql
CREATE TABLE w11_stock_txn (
    txn_id   NUMBER(10) CONSTRAINT w11_stock_txn_pk PRIMARY KEY,
    item_id  NUMBER(10) NOT NULL,
    qty      NUMBER(12,3) NOT NULL
);

INSERT INTO w11_stock_txn VALUES (1, 1, 100);
INSERT INTO w11_stock_txn VALUES (2, 1, 50);
INSERT INTO w11_stock_txn VALUES (3, 2, 70);
COMMIT;

-- Log
CREATE MATERIALIZED VIEW LOG ON w11_stock_txn
WITH ROWID, SEQUENCE (item_id, qty)
INCLUDING NEW VALUES;

-- MV: প্রতি COMMIT-এ নিজে আপডেট
CREATE MATERIALIZED VIEW w11_stock_mv
BUILD IMMEDIATE
REFRESH FAST ON COMMIT
AS
SELECT item_id,
       COUNT(*)   AS txn_count,
       COUNT(qty) AS qty_count,
       SUM(qty)   AS total_qty
FROM   w11_stock_txn
GROUP  BY item_id;

-- item 1: 150, item 2: 70
SELECT * FROM w11_stock_mv ORDER BY item_id;

INSERT INTO w11_stock_txn VALUES (4, 1, 25);

-- COMMIT-এর আগে: এখনো 150
SELECT * FROM w11_stock_mv ORDER BY item_id;

COMMIT;

-- COMMIT-এর পরে: 175
SELECT * FROM w11_stock_mv ORDER BY item_id;
```

**`FAST` Refresh-এর নিয়ম কড়া।** `SUM(x)` থাকলে `COUNT(*)` আর `COUNT(x)`-ও লাগে। নিয়ম না মানলে `ORA-12054` বা অনুরূপ এরর আসে। সব শর্ত দেখতে `DBMS_MVIEW.EXPLAIN_MVIEW` আছে, নাম জেনে রাখো।

**`ON COMMIT`-এর দাম:** প্রতিটা `COMMIT` একটু ধীর হয়, কারণ MV-ও বদলাতে হয়। ব্যস্ত টেবিলে সবাই আটকে যেতে পারে। তাই লেনদেনের টেবিলে সাবধানে ব্যবহার করবে।

### মোছা

```sql
DROP MATERIALIZED VIEW w11_stock_mv;
DROP MATERIALIZED VIEW LOG ON w11_stock_txn;
DROP TABLE w11_stock_txn;
```

## ৫. View বনাম MV (১৫ মিনিট)

| | View | Materialized View |
|---|---|---|
| কী জমা | কোয়েরি | কোয়েরি + ফল |
| জায়গা | প্রায় নেই | ডাটার মতোই |
| পড়া | ভেতরের কোয়েরির মতো | খুব দ্রুত |
| ডাটা | সবসময় টাটকা | Refresh পর্যন্ত পুরনো |
| Index | হয় না | হয় |
| DML | কিছুটা | সাধারণত না |
| কখন | সব সাধারণ কাজে | ধীর, ভারী, বারবারের রিপোর্ট |

**সিদ্ধান্তের ক্রম:**

1. কোয়েরি কি ধীর? না হলে **View**
2. Index দিয়ে দ্রুত করা যায়? (ক্লাস ৫৫, সপ্তাহ ৪০) গেলে **View + Index**
3. একটু পুরনো ডাটা চলে? চললে **MV**
4. একদম টাটকা লাগে? তাহলে কোয়েরি ঠিক করো, অথবা Trigger দিয়ে Summary টেবিল (ক্লাস ১৯)

## সারাংশ

- MV ফল জমা রাখে, পড়া দ্রুত, ডাটা Refresh পর্যন্ত পুরনো
- বানাতে `CREATE MATERIALIZED VIEW` অনুমতি লাগে
- `COMPLETE` পুরো হিসাব, `FAST` শুধু বদলানো রো (MV Log লাগে)
- `ON DEMAND` বললে, `ON COMMIT` সাথে সাথে, বাস্তবে রাতে Job দিয়ে
- আগে View আর Index, ধীর থাকলে তবেই MV

**পরের ক্লাস:** Sequence, Identity Column।
