# ক্লাস ৬৫: DCL: GRANT, REVOKE ও Role

**তারিখ:** ৩ ফেব্রুয়ারি ২০২৭, বুধবার
**সময়:** সন্ধ্যা ৭:০০ থেকে রাত ১০:০০
**সপ্তাহ:** ১৩ | **ধাপ:** ২ (Oracle SQL)

## আজকে কী শিখব

- System আর Object Privilege
- `GRANT`, `REVOKE`, কলামভিত্তিক অনুমতি
- `WITH ADMIN OPTION`, `WITH GRANT OPTION`
- Role বানানো ও ব্যবহার
- অনুমতি দেখা, ERP-তে নকশা

> আজ তিনটা কানেকশন লাগবে: `system_freepdb1` (অ্যাডমিন), `learn_freepdb1` (মালিক), `store_user` (ক্লাস ৯)।

## ১. অনুমতির ধরন (২০ মিনিট)

ক্লাস ৯-এ দেখেছিলে: Oracle-এ কেউ অনুমতি ছাড়া কিছু করতে পারে না।

| ধরন | কী দেয় | উদাহরণ | কে দেয় |
|---|---|---|---|
| **System Privilege** | ডাটাবেসে কোনো কাজ | `CREATE SESSION`, `CREATE TABLE` | অ্যাডমিন |
| **Object Privilege** | একটা নির্দিষ্ট অবজেক্টে কাজ | `learn.item`-এ `SELECT` | মালিক |

### Object Privilege

| অনুমতি | টেবিল | View | Sequence | Procedure |
|---|---|---|---|---|
| `SELECT` | ✅ | ✅ | ✅ | |
| `INSERT`, `UPDATE`, `DELETE` | ✅ | ✅ | | |
| `ALTER` | ✅ | | ✅ | |
| `REFERENCES` | ✅ | | | |
| `EXECUTE` | | | | ✅ |

**ন্যূনতম অনুমতির নীতি (Least Privilege):** যার যতটুকু দরকার, ততটুকুই। রিপোর্ট দেখে যে ইউজার, তাকে `DELETE` দেবে না।

## ২. GRANT ও REVOKE (৩০ মিনিট)

```sql
-- learn_freepdb1: মালিক দিচ্ছে
GRANT SELECT ON lib_book TO store_user;
GRANT SELECT, INSERT, UPDATE ON lib_member TO store_user;
```

```sql
-- store_user: পরীক্ষা
SELECT COUNT(*) FROM learn.lib_book;                         -- ২১
UPDATE learn.lib_member SET member_name = 'X' WHERE member_id = 1;     -- চলবে
ROLLBACK;
DELETE FROM learn.lib_member WHERE member_id = 1;            -- ORA-01031
```

### কলামভিত্তিক

`INSERT`, `UPDATE`, `REFERENCES`-এ কলাম বলা যায়। `SELECT`-এ না, তার জন্য View (ক্লাস ৫১)।

```sql
-- learn_freepdb1: শুধু মোবাইল বদলাতে পারবে
GRANT UPDATE (mobile_no) ON lib_member TO store_user;
```

### REVOKE

```sql
-- learn_freepdb1
REVOKE UPDATE ON lib_member FROM store_user;
REVOKE SELECT, INSERT ON lib_member FROM store_user;
REVOKE SELECT ON lib_book FROM store_user;
```

`UPDATE`-এর সাথে কলামভিত্তিকটাও যায়। কলাম ধরে `REVOKE` করা যায় না।

### সবাইকে: PUBLIC

```sql
GRANT SELECT ON lib_category TO PUBLIC;
REVOKE SELECT ON lib_category FROM PUBLIC;
```

ডাটাবেসের প্রতিটা ইউজার পাবে, ভবিষ্যতের ইউজারও। **প্রায় কখনোই না।**

### System Privilege

```sql
-- system_freepdb1
GRANT CREATE VIEW TO store_user;
REVOKE CREATE VIEW FROM store_user;
```

`ANY` থাকা অনুমতি (`SELECT ANY TABLE`, `DROP ANY TABLE`) সবচেয়ে বিপজ্জনক। পুরো ডাটাবেসে কাজ করে। সাধারণ ইউজারকে দেবে না।

### একটা ভুল ধারণা

```sql
GRANT ALL ON lib_book TO store_user;       -- সব Object Privilege
```

সহজ, কিন্তু ন্যূনতম অনুমতির উল্টো। এড়িয়ে চলো।

## ৩. অনুমতি হস্তান্তর (২৫ মিনিট)

**পরীক্ষার জন্য আরেকটা ইউজার:**

```sql
-- system_freepdb1
CREATE USER w13_clerk IDENTIFIED BY Clerk123;
GRANT CREATE SESSION TO w13_clerk;
```

### WITH GRANT OPTION (Object Privilege)

```sql
-- learn_freepdb1
GRANT SELECT ON lib_book TO store_user WITH GRANT OPTION;
```

```sql
-- store_user: অন্যকেও দিতে পারে
GRANT SELECT ON learn.lib_book TO w13_clerk;
```

```sql
-- w13_clerk কানেকশনে: চলবে
SELECT COUNT(*) FROM learn.lib_book;
```

### মালিক ফেরত নিলে

```sql
-- learn_freepdb1
REVOKE SELECT ON lib_book FROM store_user;
```

```sql
-- w13_clerk: এখন ORA-00942
SELECT COUNT(*) FROM learn.lib_book;
```

**চেইন ধরে সবার অনুমতি যায়।** এটাকে বলে Cascading Revoke।

### WITH ADMIN OPTION (System Privilege, Role)

```sql
-- system_freepdb1
GRANT CREATE TABLE TO store_user WITH ADMIN OPTION;
```

`store_user` এখন অন্যকে `CREATE TABLE` দিতে পারে।

**কিন্তু ফেরত নিলে চেইন ভাঙে না।**

| | `WITH GRANT OPTION` | `WITH ADMIN OPTION` |
|---|---|---|
| কীসের জন্য | Object Privilege | System Privilege, Role |
| ফেরত নিলে | **অন্যদের থেকেও যায়** | অন্যদের থেকে যায় না |

ইন্টারভিউয়ের প্রিয় প্রশ্ন।

```sql
-- system_freepdb1: পরিষ্কার
REVOKE CREATE TABLE FROM store_user;
```

## ৪. Role (৪০ মিনিট)

১০০ জন ইউজার, ৫০টা টেবিল। আলাদা করে দিলে ৫০০০টা `GRANT`। নতুন ইউজার এলে আবার। **Role** হলো অনুমতির একটা নাম দেওয়া দল।

```
টেবিলের অনুমতি  ──►  Role  ──►  ইউজার
```

### বানানো ও দেওয়া

```sql
-- system_freepdb1
CREATE ROLE w13_report_role;
CREATE ROLE w13_store_role;
```

```sql
-- learn_freepdb1: মালিক Role-কে অনুমতি দিচ্ছে
GRANT SELECT ON lib_book_detail_v TO w13_report_role;
GRANT SELECT ON lib_issue_detail_v TO w13_report_role;
GRANT SELECT ON lib_member_public_v TO w13_report_role;

GRANT SELECT, INSERT, UPDATE ON lib_book_issue TO w13_store_role;
GRANT SELECT, UPDATE ON lib_book_copy TO w13_store_role;
```

```sql
-- system_freepdb1: Role-কে ইউজারে দিচ্ছে
GRANT w13_report_role TO store_user;
GRANT w13_store_role TO w13_clerk;
```

**আবার কানেক্ট করো।** Role নতুন সেশনে কার্যকর হয়।

```sql
-- store_user, নতুন সেশনে: চলবে
SELECT COUNT(*) FROM learn.lib_book_detail_v;
SELECT COUNT(*) FROM learn.lib_book_issue;      -- ORA-00942

SELECT * FROM session_roles;
```

### Role-এর সুবিধা

- নতুন ইউজার এলে: `GRANT w13_store_role TO নতুন_ইউজার`
- নতুন টেবিল এলে: `GRANT ... TO w13_store_role`, সবার কাছে পৌঁছে যায়
- কেউ বিভাগ বদলালে: `REVOKE` পুরনো Role, `GRANT` নতুন Role

### Role-এর ভেতরে Role

```sql
-- system_freepdb1
CREATE ROLE w13_manager_role;
GRANT w13_report_role, w13_store_role TO w13_manager_role;
```

### ফাঁদ: PL/SQL-এ Role কাজ করে না

```
ইউজার:  GRANT SELECT ON learn.item TO my_role → my_role ইউজারকে দেওয়া
SQL-এ:      SELECT * FROM learn.item           → চলে
Procedure-এ: SELECT * FROM learn.item          → ORA-00942!
```

**Definer's Rights প্রসিডিওরে শুধু সরাসরি পাওয়া অনুমতি কাজ করে,** Role-এর অনুমতি না। সপ্তাহ ১৮-এ প্রসিডিওর লেখার সময় মনে রাখো। পুরনো ERP-তে এই এরর অনেক সময় নষ্ট করে।

### পরিষ্কার

```sql
-- system_freepdb1
DROP ROLE w13_manager_role;
DROP ROLE w13_report_role;
DROP ROLE w13_store_role;
DROP USER w13_clerk CASCADE;
```

`DROP ROLE` করলে যাদের ছিল, তাদের থেকে নিজে থেকে চলে যায়। `DROP USER ... CASCADE` ইউজারের সব অবজেক্টও মুছে দেয়, **সাবধান।**

## ৫. অনুমতি দেখা (১৫ মিনিট)

```sql
-- আমাকে কী কী Object Privilege দেওয়া
SELECT owner, table_name, privilege, grantor FROM user_tab_privs;

-- আমার System Privilege
SELECT privilege, admin_option FROM user_sys_privs;

-- আমার Role
SELECT granted_role, admin_option, default_role FROM user_role_privs;

-- এই সেশনে যে Role চালু
SELECT * FROM session_roles;

-- কোন Role-এ কোন টেবিলের অনুমতি
SELECT role, owner, table_name, privilege FROM role_tab_privs;

-- আমার সব টেবিলে অন্যকে কী দিয়েছি
SELECT grantee, table_name, privilege FROM user_tab_privs_made;
```

### এরর

| এরর | কারণ |
|---|---|
| `ORA-00942` | টেবিল নেই, **অথবা দেখার অনুমতি নেই** |
| `ORA-01031` | দেখার অনুমতি আছে, এই কাজের নেই |
| `ORA-00990` | অনুমতির নাম ভুল |
| `ORA-01917` | ইউজার বা Role নেই |
| `ORA-01924` | Role দেওয়া হয়নি, বা নেই |

### ERP-তে অনুমতির নকশা

**ডাটাবেস লেভেল আর APEX লেভেল আলাদা।**

| স্তর | কে | কী |
|---|---|---|
| ডাটাবেস | ডেভেলপার, DBA, রিপোর্ট টুল | এই ক্লাসের `GRANT`, Role |
| অ্যাপ্লিকেশন | Merchandiser, Store Keeper | APEX Authorization Scheme (সপ্তাহ ৩৩) |

APEX-এ সব ব্যবহারকারী একই Schema দিয়ে চলে। **Store Keeper একজন ডাটাবেস ইউজার না।** কে কোন পেজ দেখবে, তা APEX আর নিজের টেবিল দিয়ে ঠিক হয়।

ডাটাবেসের নীতিমালা:

- প্রতিটা অ্যাপের আলাদা Schema
- রিপোর্ট টুলকে শুধু View-তে `SELECT` Role
- ডেভেলপারের Production-এ `DROP`, `ALTER` অনুমতি না
- `SYS`, `SYSTEM` দৈনন্দিন কাজে না (ক্লাস ৫)
- `ANY`, `PUBLIC`, `GRANT ALL` এড়িয়ে চলো

## ৬. হাতে-কলমে প্র্যাকটিস (৫০ মিনিট)

১–৮ চালানোর আগে আগের অংশের `DROP` যদি হয়ে থাকে, তাহলে Role আবার বানাবে।

1. `w13_view_role` বানাও। `lib_book_detail_v`, `lib_copy_detail_v`-তে `SELECT` দাও। `store_user`-কে এই Role দাও। নতুন সেশনে পরীক্ষা করো।
2. `store_user`-কে `lib_member`-এ শুধু `mobile_no` কলাম `UPDATE` দাও। অন্য কলাম বদলাতে চেষ্টা করো। (`ORA-01031`)
3. `user_tab_privs_made` থেকে দেখো কী কী দিয়েছ।
4. `w13_user2` বানাও। `store_user`-কে `WITH GRANT OPTION` দিয়ে `lib_category`-তে `SELECT` দাও। `store_user` থেকে `w13_user2`-কে দাও। তারপর `learn` থেকে `store_user`-এর অনুমতি ফেরত নাও। `w13_user2`-তে কী হলো?
5. `w13_user3` বানাও। `store_user`-কে `CREATE VIEW` `WITH ADMIN OPTION` দিয়ে দাও, আর `store_user` থেকে `w13_user3`-কে দাও। তারপর `store_user`-এর অনুমতি ফেরত নাও। `w13_user3`-এর কী হলো?
6. একটা গার্মেন্টস ERP-র জন্য ৪টা Role-এর পরিকল্পনা খাতায় লেখো: `MERCH_ROLE`, `STORE_ROLE`, `PROD_ROLE`, `REPORT_ROLE`। প্রতিটায় কোন টেবিলে কী অনুমতি।
7. `role_tab_privs` থেকে `w13_view_role`-এর অনুমতি দেখো।
8. সব পরিষ্কার করো: `w13_view_role`, `w13_user2`, `w13_user3`, আর `store_user`-এর দেওয়া অনুমতি।

**ভাবো:**

9. `ORA-00942` আর `ORA-01031`-এর পার্থক্য কী? কেন Oracle "অনুমতি নেই" না বলে "টেবিল নেই" বলে?
10. একটা ফর্ম থেকে Store Keeper স্টক আপডেট করে। কোন স্তরে অনুমতি ঠিক হবে: ডাটাবেস নাকি APEX?
11. কেন Procedure-এ Role-এর অনুমতি কাজ না করার বিষয়টা জানা জরুরি?

3. `WITH GRANT OPTION`-এ ফেরত নিলে অন্যদের কী হয়?
4. Role কেন ব্যবহার করে?
5. Definer's Rights Procedure-এ Role-এর অনুমতি কাজ করে?

<details>
<summary>উত্তর দেখো</summary>

1. `GRANT`, `REVOKE`
2. System Privilege ডাটাবেসের কাজের, Object Privilege একটা নির্দিষ্ট অবজেক্টের
3. চেইন ধরে তাদেরও চলে যায়
4. অনেক অনুমতি এক নামে দিতে, সহজে ম্যানেজ করতে
5. না, সরাসরি `GRANT` লাগে

</details>

## সারাংশ

- Object Privilege মালিক দেয়, System Privilege অ্যাডমিন দেয়
- ন্যূনতম অনুমতি দাও। `ANY`, `PUBLIC`, `GRANT ALL` এড়িয়ে চলো
- `WITH GRANT OPTION` ফেরতে চেইন ভাঙে, `WITH ADMIN OPTION` ভাঙে না
- Role: অনুমতির দল। নতুন সেশনে কার্যকর। Procedure-এ কাজ করে না
- ডাটাবেস অনুমতি আর APEX Authorization আলাদা
